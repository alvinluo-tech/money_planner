# Money Planner · 会听你说话的旅行记账

> 语音说一句「午饭 15 镑，地铁 3 镑」，账就记好了；AI 每天告诉你这趟 13 天的行程还撑不撑得住。

一个**为旅行设计**的记账应用。不是把日常记账 App 换个皮，而是围绕三件事重做：

1. **零输入摩擦** —— 说话记账，不用点开表单填七项字段。
2. **多币种预算** —— 预算可以是 `1000 GBP + 10000 CNY` 这种组合，消费自动折算。
3. **会做判断的 AI** —— 不只是画图表，而是回答「按现在的节奏，这趟旅行会不会超支」。

---

## 一、技术选型：Next.js + Supabase 合适吗？

**合适，而且这是这个需求的最佳组合之一。** 具体理由：

| 需求 | 为什么这个栈合适 |
| --- | --- |
| 语音上传 + 调大模型 | 需要服务端持有 API Key。Next.js Route Handler 天然就是这层「后端」，不用再起一个服务。 |
| 手机随手记账 | 移动端浏览器 / 加到主屏幕即可，PWA 化成本低。 |
| 账号 + 数据隔离 | Supabase Auth + **RLS 行级安全**，一条 SQL 策略就让「别人读不到你的账本」，不用自己写权限层。 |
| 实时同步（两人一起记账） | Supabase Realtime 订阅即可，几乎零代码。 |
| 快速迭代 | Postgres + 迁移文件，schema 改动比手写 ORM 迁移轻。 |

**几个我特意做的技术决策：**

- **不引入 LLM SDK，只写了一个 200 行的 OpenAI 兼容客户端**（`src/lib/ai/chat.ts`）。
  改 `AI_BASE_URL` 就能在 OpenAI / DeepSeek / 通义千问 / Moonshot / 智谱 / Ollama 之间切换，没有 SDK 版本兼容负担。
- **模型永远不碰数字。** 预算判断全部由 `src/lib/budget.ts` 的纯函数算出来，模型只负责「把数字讲成人话 + 给建议」。所以模型胡说也不会污染账本。
- **每条记录冻结当时的汇率**（`fx_rate` + `base_amount` 一起落库）。日后汇率波动不会改写历史账目。
- **语音有多级降级**：云端 STT → 浏览器本地识别 → 纯文字输入 → 本地规则解析。任何一环挂了都还能记账。
- **没有 Supabase 凭据也能跑**：自动进入内存演示模式，预置一趟 13 天英国行程，零配置就能看效果。

## 二、快速开始

```bash
pnpm install
pnpm dev          # → http://localhost:3000
```

**零配置**：直接打开就是演示模式（内存数据，预置了 1000 GBP + 10000 CNY 的英国行程和 14 笔消费）。

### 接入真实 Supabase

1. 建一个 Supabase 项目，执行迁移（二选一）：
   - 在 SQL Editor 里按顺序执行 `supabase/migrations/` 下的 4 个文件；或
   - 用 CLI 推送：`supabase db push --db-url "<连接串>"`，连接串在 Dashboard → Connect 里复制
     （Session pooler 那条 URI，形如 `postgresql://postgres.<项目ref>:<密码>@aws-1-<区域>.pooler.supabase.com:5432/postgres`）。
2. `cp .env.example .env.local`，填入 `NEXT_PUBLIC_SUPABASE_URL` 和 `NEXT_PUBLIC_SUPABASE_ANON_KEY`。
3. 重启 `pnpm dev`。会自动切换到 Supabase 模式并跳转登录页（6 位邮箱验证码登录，不依赖点击任何链接）。
4. Supabase Dashboard → Authentication → URL Configuration：
   - **Site URL** 填你实际访问的地址（例如 `http://localhost:3000`）
   - **Redirect URLs** 加上 `http://localhost:3000/auth/callback`
5. `NEXT_PUBLIC_SITE_URL` 必须和实际访问端口一致。不一致的话登录页会直接标红提醒（这是「邮件链接打不开」最常见的原因）。

> **收不到验证码？** 登录页默认用 **6 位验证码**：验证码在当前浏览器里输入，不依赖点击邮件里的任何链接，天然没有「链接在另一个浏览器打开」的问题。收不到邮件先看垃圾箱，再看下面的检查清单（登录页底部有同样的内容）。最常见的三个原因：
> 1. `NEXT_PUBLIC_SITE_URL` 的端口和实际访问端口不一致 → 回调地址没有服务；
> 2. Supabase 的 Redirect URLs 没登记 → 回调被拒；
> 3. Supabase 免费内置发信限流严、容易进垃圾箱 → 按下一节接入 Resend。

### 配置 Resend 发信（可选，强烈建议）

Supabase 免费内置发信每小时只有几封的配额，且容易被判为垃圾邮件。换成 Resend（免费档 3000 封/月）：

1. 注册 [resend.com](https://resend.com)，**Domains → Add Domain** 绑定你自己的域名，按提示去 DNS 服务商加 SPF/DKIM 记录并等验证通过。
   ⚠️ 没有自己的域名时，Resend 只允许用 `onboarding@resend.dev` 发给你 Resend 账号自己的邮箱——**其他人的邮箱收不到**（姐姐就登录不了）。没域名就先用 Supabase 内置发信，或买个便宜域名。
2. **API Keys → Create API Key**，生成 `re_` 开头的密钥（只显示一次）。
3. Supabase Dashboard → **Project Settings → Authentication → SMTP Settings**，启用 Custom SMTP：
   | 字段 | 填什么 |
   | --- | --- |
   | Sender email | `noreply@你的域名`（必须是已验证的域名） |
   | Sender name | `Money Planner` |
   | Host | `smtp.resend.com` |
   | Port | `465` |
   | Username | `resend` |
   | Password | 你的 `re_` API Key |
   | Minimum interval | `60` |
4. **Authentication → Emails → Templates → Magic Link**，把 HTML 正文替换为项目里的
   `supabase/templates/magic-link-zh.html`（登机牌样式的验证码邮件），邮件主题建议：
   `【Money Planner】登录验证码 {{ .Token }}`。模板只需用到 `{{ .Token }}`（邮箱验证码）这一个变量。验证码位数由项目配置决定（Authentication → Providers → Email 里的 OTP Length，6 或 8 位），登录页两种长度都兼容。

### 接入大模型（可选，但强烈建议）

`.env.local` 里填任意一家 OpenAI 兼容端点：

```bash
AI_API_KEY=sk-xxx
AI_BASE_URL=https://api.deepseek.com/v1   # 或 https://api.openai.com/v1
AI_MODEL=deepseek-chat

# 语音识别（可复用同一家）
STT_API_KEY=sk-xxx
STT_BASE_URL=https://api.openai.com/v1
STT_MODEL=whisper-1
```

> 不填也能用：解析会退回**本地规则引擎**，中文口语识别率相当不错（见测试用例），只是复杂句式和分类判断不如大模型。

## 四、核心流程

### 1. 语音 → 账本

```
麦克风 ──► MediaRecorder ──► POST /api/capture
                              │
                              ├─ 云端 STT（whisper 等）──┐
                              └─ 浏览器 SpeechRecognition ┴─► 文本
                                                            │
                      大模型（JSON mode + zod 校验 + 失败重试一次）
                                                            │
                                    失败 ──► 本地规则引擎 ◄──┘
                                                            │
                                         结构化草稿（多条）──► 用户确认/修改
                                                            │
                                                  POST /api/expenses（补汇率落库）
```

- 一句话里多笔消费会自动拆分：「午饭 15 镑，地铁 3 镑，超市 22 镑」→ 3 条。
- 每条带 **置信度**，低的会被标出来让你重点核对。
- 大模型会读取你**最近 6 条真实记账样本**，学习你本人的表达习惯（比如你总说「打优步」而不是「打车」）。

### 2. 预算推演（`src/lib/budget.ts`）

给定：行程起止、多币种预算、已发生消费、当前汇率。

```
总预算(基准币) = Σ 各币种预算 × 汇率
实际日均       = 已花 / 已过天数
健康日均       = 剩余预算 / 剩余天数
预计总支出     = 已花 + 实际日均 × 剩余天数
预计超支       = max(0, 预计总支出 − 总预算)
可支撑天数     = 剩余预算 / 实际日均
```

健康度判定：

| 状态 | 条件 |
| --- | --- |
| `on_track` | 预计不超支 |
| `watch` | 预计超出预算但在 15% 以内 |
| `at_risk` | 预计超出预算 15% 以上 |
| `over_budget` | 已经花超 |

还会生成**消费结构诊断**：每个分类对比旅行场景的建议占比（住宿 30%、餐饮 22%、交通 12%…），超出 1.4 倍就提示「占比偏高」。

### 3. 多国行程：行程分段（legs）

一趟旅行去多个国家时，「单一目的地 + 单一默认币种」会到处出错。所以引入**行程分段**：
每一段 = 一个国家/城市 + 日期区间 + 币种 + 时区。

```
trip_legs: 伦敦(GBP, Europe/London, 09-05~09-08)
        → 巴黎(EUR, Europe/Paris,   09-09~09-12)
        → 苏黎世(CHF, Europe/Zurich, 09-13~09-17)
```

它解决四类问题：

| 场景 | 没有分段 | 有分段 |
| --- | --- | --- |
| 在巴黎说「午饭 15」（没说币种） | 按预算里第一个非基准币猜，可能记成 15 英镑 | **15 EUR** |
| 在巴黎说「昨天午饭 15」，而昨天在伦敦 | 按今天所在的欧元区记成 15 EUR | **15 GBP**（按消费发生那天所在的段） |
| 伦敦飞东京后的「今天」 | 按出发地时区算，跨零点差一天 | 按当前所在段的时区算 |
| 想知道「法国段花得快不快」 | 无从算起 | 分段进度 + 参考额度 |

**三条设计原则：**

1. **分段是「推断用元数据」，绝不回溯改写历史。** 已落库的 `amount / currency / fx_rate / base_amount` 是冻结的；事后修改分段只影响分段视图，不改动任何账目数字。
2. **分段完全可选。** 不配分段时行为与单国行程完全一致（用 `trips.timezone` + 预算推断币种），老数据零迁移。
3. **允许首尾相接。** 上一段结束日 == 下一段开始日（转机日）时，那天算进后一段——你多半已经在新国家消费了。真正重叠会被校验拒绝。

分段没覆盖的日期（转机停留、休息日、回程日）会回退到行程级默认币种。

参考额度 = 全程预算 × 该段天数占比，**只是参照物**：跨国旅行里机票和长途交通集中在移动日，按天数摊平天然会让移动日显得紧、度假日显得松。

### 4. 语音纠错：直接改掉刚记错的那一笔

说「刚才那笔改成 18 镑」「昨天那笔删掉」「在星巴克那笔改成 5 欧」，不会新增记录，而是：
解析出意图（correct / delete）→ 定位目标（最近一笔 / 按日期 / 按商家）→ 前端展示「原 → 新」对比 → 确认后 PATCH 或 DELETE。

- 大模型路径给出 `correction.target` + `correction.changes`（只带真正要改的字段，没说到的沿用原值）。
- 规则路径靠触发词（改成/改为/应该是/记错了/不是…是/删掉）识别，定位支持「刚才/上一笔/最后一笔」「昨天那笔」「在X那笔」。
- 服务端负责把「刚才那笔」解析成具体记录（`resolveCorrectionTarget`），前端只做确认，不猜。

### 5. AI 助手：多轮记忆 + 工具调用 + 流式输出

入口在「分析」页的 **问 AI** 标签（`/trips/:id/insights?tab=chat`），明细页搜索框也能一键把问题带过去。

- **多轮记忆**：会话存在 `ai_threads` / `ai_messages`，下一轮会带上最近的 user/assistant 文本。
- **工具调用**：模型自己决定调哪个工具，数字全部来自真实数据 ——
  - `query_expenses`：按日期/分段/分类/商家/币种/金额查明细，支持按金额排序（「最贵的一顿」）
  - `aggregate_expenses`：按分类/币种/分段/天汇总
  - `get_budget_summary`：预算、剩余、日均、预计超支、分段进度
- **流式输出**：`/api/assistant` 用 SSE 返回 `thread / token / tool / done / error` 事件，前端逐字渲染，工具调用会在气泡上方显示「🔧 查询消费明细 · 查到 29 笔，返回 1 条」。
- **最多 4 轮工具往返**，防止死循环。
- 没配 `AI_API_KEY` 时明确提示，并引导回明细页的本地搜索（不会假装能用）。

### 6. AI 分析

模型拿到的是**已经算好的确定性数字** + 最近 25 笔明细，输出：一句话结论、严重程度、分析正文、关键观察、**可执行动作**（"把接下来日预算控制在 ¥1,245 以内"这种，不是"注意节省"）。

还可以追问：「我还能买那个 300 镑的包吗」→ 模型基于剩余预算和剩余天数回答。

### 一轮完整审计中修掉的问题

| # | 问题 | 影响 | 修法 |
| --- | --- | --- | --- |
| 1 | 内存演示数据用模块级变量 | **生产构建下每个 route/page 各有一份副本**，API 写入的消费页面根本读不到 | 改挂 `globalThis`（`memory.ts`） |
| 2 | 演示种子消费全落在未来日期 | 「今日支出」虚高、累计趋势把没花的钱算成已花 | 种子改为行程已过去的 -4~0 天 |
| 3 | 超支提醒引用错金额 | 文案显示「已花 = 预算总额」 | 传入真实 `spent` |
| 4 | 轻微超支也报 critical | 提醒级别与健康度标签矛盾 | 超支 <10% 降为 warn |
| 5 | 未登录访问 `/api/*` 返回 307 跳登录页 | 调用方拿到 HTML 而非 401 JSON | API 路径改返回 401 JSON |
| 6 | 「一起」「一共」被识别成 1 元 | 凭空多出一笔消费 | 中文数字只在后接货币词或前有记账语境时展开 |
| 7 | 关闭语音面板后回填过期数据 | 下次打开看到上次的解析结果 | 加 abort 标记丢弃在途响应 |
| 8 | 只有一个行程时进不去列表 | 无法新建第二个行程 | `/?all=1` 强制回列表 + 侧边入口 |
| 9 | 行程只能建不能改/删 | 功能不完整 | 新增 `PATCH/DELETE /api/trips/:id` + 设置页表单 |
| 10 | `capture_logs` 状态永远停在 pending | 审计链路断裂 | `/api/capture` 返回 `captureId`，落库时回写 confirmed |
| 11 | 写接口无同源校验 | CSRF 纵深防御缺失 | `withMutation` 校验 Origin/Host |
| 12 | 改基准币会让历史折算失真 | 数据一致性隐患 | 已有消费时拒绝修改（409） |
| 13 | 未知币种被静默按 1:1 折算 | 金额直接算错且无提示 | 汇率兜底改返回 0；输入层用 `isSupportedCurrency` 拒绝 |
| 14 | 模型可能返回不存在的币种 | 落库时才失败 | 解析层回退到目的地默认币种 |
| 15 | **多国行程币种推断错** | 在巴黎说「昨天午饭 15」按今天所在的欧元区记成 EUR | 引入行程分段，按「消费发生那天」所在的段推断 |
| 16 | **跨时区日期错** | 单一 `timezone`，「今天」跨零点差一天，未来日期兜底还会改写 | 「今天」按当前所在段的时区算 |
| 17 | **数据模式自相矛盾** | `APP_DATA_MODE=demo` 时页面走演示模式，中间件却仍要求登录 | 抽出 `data-mode.ts`，中间件与 db 层共用同一判定 |
| 18 | **魔术链接「打不开」** | `NEXT_PUBLIC_SITE_URL` 端口与实际访问端口不一致，链接跳到空地址 | 改用当前实际地址申请链接 + 端口不一致告警 + 回调错误码细分 |

### 第二轮审计修复（独立复审发现）

### 已知取舍与限制

- **演示模式**只适合本机 / 单实例（数据在进程内存里，重启即重置）。要持久化请配置 Supabase。
- **AI 与语音接口没有限流**。个人自用没问题，公开部署前建议按用户加频率限制。
- **消费落库没有幂等键**。网络超时重试理论上可能产生重复记录（客户端已禁用重复提交，但服务端没有去重）。
- **汇率只做进程内缓存**；`fx_rates` 表已建好，留给定时任务做跨实例缓存与历史审计。
- **没有实时多端同步**，多人共同记账需要接 Supabase Realtime（见路线图第 9 条）。

## 六、移动端设计约定

这个应用按「手机为主」设计，几条硬性约定写在 `src/app/globals.css` 里：

| 约定 | 原因 |
| --- | --- |
| 所有可点元素 `min-height: 44px`（`.btn` / `.chip` / `.input` / `.icon-btn`） | 拇指点击的可靠下限，分类选择是最高频操作 |
| 输入框在 <640px 时字号 16px | iOS Safari 对 <16px 的输入框会自动放大整页，体验极差 |
| 不设 `maximumScale` | 禁止缩放会让看不清小字的用户无路可走（WCAG 1.4.4） |
| `viewport-fit=cover` + `env(safe-area-inset-bottom)` | 底部标签栏与语音按钮不被 Home 指示条遮挡 |
| 面板用 `dvh` 而非 `vh` | iOS 键盘弹起时输入框不会被键盘盖住 |
| 文本对比度 ≥ 4.5:1（`--color-ink-muted` = #6f665e） | 原来 3.5:1 不达标 |
| 全局 `active:` 按压反馈 + `touch-action: manipulation` | 触屏没有 hover，且要消除 300ms 点击延迟 |
| 底部标签栏（4 项）+ 中间悬浮语音按钮 | 手机上的拇指热区，桌面端自动切回顶部标签 |

明细页的搜索与筛选在客户端本地完成，输入即时响应，不往返服务端。

## 七、接下来可以加什么（按优先级）

### 🔥 强烈建议（旅行场景的真实痛点）

1. **收据拍照识别**
   语音说不清店名和精确金额时补一刀。一张小票常常是 3~5 笔，VLM 一次搞定，比语音更准。这是语音之外的第二条低摩擦入口。

2. ~~AA 分账~~ —— **已确认不需要**：家人同游、不 AA，消费记在一本账上即可。

3. **预算分层：总预算 / 每日额度 / 分类额度 + 机动池**
   把 1000 英镑里的 200 划成「机动/购物专用」，日常只按 800 的节奏跑。超支时先吃机动池，而不是直接判定失败——心理上更好坚持。

4. **已支付 vs 待支付**
   机票、住宿常常提前付了。如果全算进「今日节奏」，第一天就会显示日均爆炸。需要一个 `is_prepaid` 标记，让节奏计算只看出行期间的现金流。

5. **离线优先（PWA + 本地队列）**
   境外地铁里没网是常态。录音和记账先写 IndexedDB，联网后自动同步。**这是让「随手记」真正成立的关键。**

6. **真实成本提示**
   境外刷卡手续费、ATM 取现费、以及最坑的 **DCC 动态货币转换**（在刷卡机上选"以人民币结算"通常多付 3~5%）。记一笔时提示一下，能实打实省钱。

### 👍 值得做

7. **语音纠错**：「刚才那笔改成 18 镑」——直接改最近一条，不用点进明细。
8. **每日复盘推送**：晚上 9 点一条通知「今天花了 ¥412，还剩 ¥11,204，明天建议 ¥1,245 以内」。
9. **共同账本**：邀请姐姐加入，实时看到同一份预算（Supabase Realtime 几乎零成本）。
10. **信用卡账单导入**：CSV/PDF 导入兜底补录，比逐笔补记快。
11. **行程联动预警**：知道第 8 天有 120 镑的城堡门票，提前把那天额度调高，避免「假超支」。
12. **数据导出**：CSV / Excel，旅行结束留档。

### ✨ 锦上添花

13. 地图热力（钱都花在哪个区域）
14. 旅行结束生成可分享的「消费报告」长图
15. 汇率提醒（英镑跌破 9.0 时提示可以换汇）
16. 订阅/固定支出自动识别
